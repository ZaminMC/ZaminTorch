# 1. THE ACTUAL MISSION

Torch has two inseparable goals:

### A. Independent engine architecture

Build a real multicore Minecraft server architecture based on explicit state ownership, controlled mutation, safe parallel computation, and explicit cross-owner coordination.

### B. Faithful Minecraft 1.8.8 gameplay

Reproduce observable 1.8.8 behavior: formulas, constants, arithmetic, rounding, tick order, entity order, block updates, collisions, inventory transactions, damage, redstone, AI, world generation, packets, legacy quirks, and cross-system interactions.

The concurrency architecture exists to run the gameplay layer safely. The gameplay layer determines which operations are actually safe to parallelize.

Do not design a generic concurrency framework first and discover later that vanilla mechanics cannot use it.

# 6. PERMANENT CONCURRENCY MODEL

## 6.1 Logical ownership

An ownership domain is the authority over a defined set of mutable state.

A physical worker is only an execution resource.

An owner may run on different workers over time. A worker may run many owners. Never define ownership using thread identity, thread name, executor identity, or `ThreadLocal` alone.

The execution context must carry something equivalent to:

`owner-id + owner-generation + execution-authority`

## 6.2 One authoritative writer

Normal authoritative mutation belongs to the current logical owner.

“Single writer” means single **logical authority**, not one permanent OS thread.

## 6.3 Stale work must be harmless

Every asynchronous result capable of touching mutable state must carry enough version/generation information for the receiving owner to validate it.

If generation `G1` produced a result and the state is now at `G2`, the result cannot mutate the state.

Reject, cancel, or recompute stale work.

## 6.4 Mutable references do not cross owners casually

Do not hand another owner a live mutable entity, inventory, chunk, block entity, collection, or world object.

Use immutable values, snapshots, commands/intents, or explicit request/result protocols.

## 6.5 Parallel computation is separate from authority

Pathfinding, AI planning, lighting, world generation, serialization, compression, persistence preparation, and similar calculations may execute off-owner when their inputs are explicit.

Their result must return to the authoritative owner for validation and publication.

# 7. INITIAL SCHEDULER CONTRACT

Evaluate practical scheduler designs, then select one. Do not endlessly compare them.

The initial scheduler must provide:

- a shared physical worker pool rather than one OS thread per player/chunk/region;
- multiple independent owners progressing concurrently;
- no conflicting authoritative tasks for the same owner running simultaneously;
- idle owners consuming negligible CPU;
- fairness so one busy owner cannot permanently consume every worker;
- bounded queue growth;
- cancellation and shutdown;
- delayed task ordering;
- diagnostics for queue latency and starvation.

**Work stealing may move an eligible task between physical workers. It never moves mutation authority.**

A worker may execute owner work only after entering that owner's validated execution context.

Do not prematurely split every entity/block operation into tiny tasks. Task overhead and ordering are part of the design.

### Four proof cases

**Hopper:** define inventory ownership and an atomic/no-duplication transfer protocol when source and destination belong to different owners.

**Piston:** define how a piston affecting blocks in multiple owners validates all affected state and commits the movement in the correct order.

**Entity + AI:** define how a pathfinding/AI result becomes stale after movement or migration and how it is rejected/recomputed.

**Migration:** define what happens to queued tasks, delayed tasks, messages, snapshots, and compute results across a generation change.

If these are vague, the concurrency design is incomplete.

# 11. HEAVY OWNER / “BEYOND FOLIA” STRATEGY

Do not promise arbitrary concurrent Minecraft mutation.

Use four levels:

### Level A — independent owners

Independent domains simulate concurrently.

### Level B — parallel support computation

Pathfinding, AI planning, generation, lighting, serialization, persistence preparation, etc.

### Level C — intra-owner computation

Use immutable snapshots, dependency declarations, disjoint work, intents, version validation, and deterministic commit to parallelize selected calculations inside a busy owner.

### Level D — concurrent authoritative mutation

Only where the state is genuinely independent and a complete ownership/conflict protocol exists.

Level D is future research until proven. Do not build a huge speculative conflict framework before A/B are working.

**Parallel calculation does not grant parallel mutation rights.**

# 27. TORCH API ARCHITECTURE — COMPLETE ENGINE EXPOSURE

## 27.1 Product intent

Torch is not intended to stop at Bukkit-, Spigot-, Paper-, or Folia-level API coverage. Its native API must expose the full useful capability of the Torch engine, including low-level control over Minecraft mechanics. Developers must not have to wait for Torch maintainers to approve or invent a higher-level abstraction before they can use an engine capability.

The API is a first-class part of Torch, not a later wrapper around Bukkit and not a compatibility feature that can be postponed indefinitely.

The intended order is:

1. Recreate and verify Minecraft Java Edition 1.8.8 mechanics.
2. Build Torch's engine and native API together, exposing implemented capabilities as they become real and testable.
3. Polish the 1.8.8 implementation into a playable, maintainable server.
4. Build the Bukkit/Spigot/Paper compatibility layer over the mature Torch engine and API.
5. Add further Minecraft versions as version-specific mechanics implementations backed by the continuing Torch engine and API contracts.

Do not delay the native API until the compatibility layer exists. Do not design the native API as a copy of Bukkit's limitations.

## 27.2 Architectural shape

The intended dependency direction is:

`Minecraft-version mechanics implementation → Torch engine capabilities → Torch native API → plugin integrations and compatibility adapters`

This describes conceptual boundaries, not permission to create unnecessary modules before the codebase needs them.

### A. Version-specific mechanics

This layer implements the observable mechanics and protocol behavior of a particular Minecraft version. Initially that means 1.8.8: its movement, collision, combat, AI, block behavior, inventories, redstone, scheduled updates, world generation, entity metadata, packets, and quirks.

Version-specific behavior must remain explicit. Do not pretend two Minecraft versions are equivalent merely because their concepts have similar names.

### B. Torch engine

This owns authoritative state, simulation, lifecycle, storage, scheduling, networking infrastructure, ownership enforcement, and execution protocols. It supplies mechanisms that version implementations use without silently replacing their version-specific behavior with modern defaults.

### C. Native Torch API

This is the documented, supported developer-facing surface over engine capabilities. It should expose both convenient abstractions and deep control. A high-level API and a low-level API are complementary entry points to the same authoritative engine, not separate game states.

### D. Compatibility adapters

Bukkit/Spigot/Paper compatibility belongs above the native engine/API boundary. It translates legacy contracts into Torch operations and adapts lifecycle, events, scheduling, objects, and expected behavior. It must not become Torch's internal architecture or dictate that the native API expose only what Bukkit exposes.

## 27.3 Complete exposure is the goal

For every meaningful engine subsystem, the native API design must answer: what can a plugin observe, query, register, replace, intercept, or mutate?

The inventory of capabilities must be discovered from the actual implementation and maintained as the engine grows. At minimum, audit and plan public access for:

- world, chunk, block, block-state, block-entity, and world-generation operations;
- entities, entity lifecycle, attributes, metadata, movement, gravity, friction, collision, damage, knockback, and death;
- mob AI, goals, navigation, pathfinding inputs/results, target selection, and behavior control;
- player state, inventory, equipment, item use, crafting, containers, experience, hunger, health, and combat;
- block placement/breaking, drops, neighbor updates, scheduled block/fluid ticks, redstone, pistons, explosions, and hoppers;
- entity tracking, replication, metadata, packet construction/inspection/interception, and connection lifecycle;
- commands, permissions, events, plugin lifecycle, registries, configuration, and server lifecycle;
- scheduler/task controls, owner-context execution, cross-owner requests, snapshots, and safe asynchronous computation;
- diagnostics, timings, tracing, metrics, and supported inspection of internal engine state.

This list is a minimum audit checklist, not a claim that all capabilities already exist. Add capabilities when code inspection discovers them. Record any inaccessible capability and the concrete reason; do not omit it merely because it is low-level or inconvenient to expose.

Where a subsystem has internal stages or extension points that materially affect behavior, consider public hooks for those stages rather than exposing only a final setter. Examples include AI goal evaluation, movement/collision decisions, damage processing, block-update propagation, inventory transfer decisions, entity tracking, and packet processing.

## 27.4 API completeness and stability are separate properties

Torch should aim for broad, deep capability without accidentally promising that every implementation class is immutable forever.

Classify API contracts explicitly:

- **Stable:** documented compatibility commitment. Breaking changes require a deliberate versioning/migration policy.
- **Experimental:** usable and documented, but may change while the design is being proven.
- **Internal:** implementation detail with no plugin compatibility guarantee.

Do not use these labels to hide essential engine capabilities indefinitely behind an inaccessible internal layer. If developers need a capability to control or extend a mechanic, provide a documented API route for it. When a capability is experimental, expose it honestly as experimental.

Keep stable API contracts independent of internal storage layouts where practical. A stable contract may be implemented by a different class, data structure, or algorithm in a later release.

## 27.5 Wrappers, handles, and implementation replacement

Use stable API-facing interfaces, handles, facades, or adapters where they create a real boundary between plugins and mutable engine implementation. The API-facing object must represent the authoritative engine object; it must not become a second copy of game state.

For example, a public entity handle can remain stable while the internal entity implementation changes. Calls through that handle must resolve to the current authoritative state and respect lifecycle and ownership checks.

Requirements:

- Public API types must not require plugins to cast to internal implementation classes for ordinary supported operations.
- Do not expose mutable internal collections or raw mutable references that bypass ownership enforcement.
- Avoid one wrapper per access or other allocation-heavy patterns without measurement; wrapper identity and lifetime semantics must be documented.
- Define behavior for invalid, removed, unloaded, or migrated objects.
- Keep access to advanced mechanics possible through explicit low-level interfaces, not undocumented reflection into implementation classes.
- Do not create a wrapper hierarchy merely for appearance. Every boundary must have a defined responsibility.

Wrappers cannot magically preserve compatibility when a plugin depends on removed behavior, private fields, object identity, or bytecode-level implementation details. The compatibility plan must distinguish supported contracts from best-effort translation.

## 27.6 Low-level access must obey ownership, not bypass it

Full API exposure means broad capability, not unrestricted mutation from arbitrary threads.

The native API must expose the operations developers need while preserving Torch's concurrency contract:

- Read-only snapshots and immutable views may be consumed off-owner according to their documented consistency guarantees.
- Live-state reads must declare whether they require owner context, provide a snapshot, or are safe through a synchronized/versioned read protocol.
- Mutations must execute under the authoritative owner's validated context or use an explicit command/intent/request protocol.
- Cross-owner actions must define ordering, validation, cancellation, stale-result handling, and failure behavior.
- Asynchronous computation must not receive a live mutable object and treat possession of its reference as authority.
- Development builds should identify illegal access with useful diagnostics.
- The API must not silently turn a familiar synchronous method into a blocking cross-owner RPC.

These constraints must be reflected in method signatures, documentation, and tests. Do not make concurrency safety an undocumented burden that plugin authors must infer.

## 27.7 Extensibility at the mechanics level

A complete API should support more than reading state and calling setters. For each major mechanic, evaluate extension points such as:

- observing and cancelling applicable operations where cancellation is semantically valid;
- registering additional behavior or goals;
- replacing or composing selected strategies;
- querying intermediate decisions and their reasons;
- supplying custom implementations through explicit extension contracts;
- observing the result after authoritative validation/commit;
- intercepting protocol operations with clearly defined ordering and security boundaries.

Do not add every hook speculatively. Implement hooks alongside the real mechanics, with explicit ordering, reentrancy, cancellation, exception, and concurrency semantics. Hooks must not permit a plugin to bypass the authoritative state owner.

## 27.8 Versioning the engine and mechanics

The long-term design must separate three concerns:

1. **Torch engine contracts:** reusable infrastructure and ownership/scheduling rules.
2. **Minecraft-version behavior:** version-specific mechanics and protocol semantics.
3. **Native API contracts:** the documented capabilities plugins compile against.

Do not assume the same API can represent every version without version-specific types or explicit capability differences. Preserve stable common contracts where their semantics genuinely match; expose version-specific behavior through deliberate versioned/capability surfaces where they do not.

A later version must not silently change the meaning of a 1.8.8 operation. Compatibility must be semantic, not merely a matching method name.

## 27.9 Bukkit/Spigot/Paper compatibility strategy

Compatibility is a later integration milestone, after Torch's native engine/API and 1.8.8 behavior are sufficiently mature. Its goal is to run existing plugins with as little modification as practicable, but compatibility claims must be evidence-based.

Build a compatibility inventory covering:

- public API signatures and binary linkage;
- plugin discovery, loading, dependencies, lifecycle, and classloading;
- event registration, priorities, cancellation, ordering, and exception behavior;
- commands, permissions, scheduling, and plugin-owned tasks;
- world/entity/player/block/inventory object semantics;
- metadata, persistent/plugin data, registries, and configuration expectations;
- server internals/NMS and CraftBukkit access;
- reflection, method/field lookups, package names, generated bytecode, and version checks;
- assumptions about a single main thread and synchronous world mutation;
- Paper/Spigot-specific APIs and plugin descriptors.

Use layered adapters and compatibility tests. Prefer translating supported API calls to native Torch operations rather than recreating a parallel Bukkit world model.

Do not promise that every plugin will run seamlessly until a representative test suite demonstrates it. Plugins that directly depend on NMS, CraftBukkit internals, private implementation details, exact bytecode, or undocumented timing behavior may need version-specific shims or may be unsupported. Record those limitations precisely instead of overstating compatibility.

## 27.10 API compatibility tests and capability ledger

Maintain a native API capability ledger alongside `VANILLA_1_8_8_COMPATIBILITY.md`. For each subsystem record:

- engine capability and source implementation;
- public API entry point;
- allowed observations and mutations;
- required execution/ownership context;
- extension hooks;
- stability classification;
- behavioral and concurrency tests;
- known omissions and rationale;
- status: `NOT AUDITED → AUDITED → IN PROGRESS → IMPLEMENTED → VERIFIED / BLOCKED`.

Add tests proving that plugins can perform meaningful low-level operations through the public API without depending on internal classes. Add negative tests proving the API rejects or safely routes illegal cross-owner mutation. Test wrapper behavior across entity removal, chunk unload, migration, and implementation replacement.

A capability is not considered exposed merely because a public method exists. It must be usable, correctly documented, behaviorally meaningful, and covered by tests.

## 27.11 API implementation workflow

When implementing each mechanics subsystem:

1. inspect and understand the exact 1.8.8 reference behavior;
2. implement the authoritative mechanics in Torch;
3. enumerate the subsystem's meaningful observable state, mutations, decisions, and extension points;
4. expose those capabilities through the native API at an appropriate level of abstraction;
5. ensure API calls obey ownership and lifecycle rules;
6. test gameplay behavior and public API behavior together;
7. document stability, ordering, consistency, and failure semantics;
8. record unexposed capabilities and explain why they remain unavailable;
9. update both the vanilla compatibility ledger and native API capability ledger.

Do not finish a subsystem by implementing only the mechanics while leaving developers unable to inspect or control important parts of it. Do not invent APIs disconnected from implemented behavior. Engine and API should mature together.

## 27.12 Definition of success

Torch succeeds at its native API goal when developers can inspect, extend, replace, and control the meaningful mechanics implemented by the engine without being arbitrarily limited to high-level convenience methods; when those capabilities have explicit and testable execution semantics; and when internal implementation changes can be absorbed by stable API boundaries where the underlying contract has not changed.

The governing principle is:

**Expose the engine's capabilities, not merely the abstractions Torch maintainers happen to anticipate. Preserve contracts deliberately, and enforce safe execution without withholding useful control.**

# 28. PLUGIN CONCURRENCY, DEADLOCKS, AND LIFECYCLE — REQUIRED CONTRACT

This section makes plugin safety a first-class part of Torch's engine and native API architecture. Plugins are untrusted with respect to correctness: even well-intentioned plugin code may block, re-enter callbacks, retain stale references, throw exceptions, or access state from the wrong execution context. Do not assume that plugin authors understand Torch's ownership model.

The goal is not to restrict plugins to a shallow API. The goal is to expose deep engine control through explicit, enforceable execution contracts.

## 28.1 Required plugin execution model

Every plugin callback and task must have a documented execution category. At minimum distinguish:

1. **Authoritative gameplay callback:** runs in a validated owner context and may perform only the mutations allowed to that owner.
2. **Snapshot/read callback:** receives immutable or explicitly versioned data and has no implicit mutation authority.
3. **Asynchronous computation:** runs on a bounded compute executor using immutable inputs; returns a result or intent for validation by the authoritative owner.
4. **Blocking I/O task:** database, filesystem, HTTP, or other potentially blocking work runs outside simulation workers and returns results through a defined handoff.
5. **Lifecycle/control callback:** load, enable, disable, reload, and shutdown have explicit threading, timeout, and resource-cleanup semantics.

Do not let a callback's execution category be inferred from its method name or the thread that happens to run it. The API and diagnostics must identify the actual context.

A plugin-created thread does not acquire authority to mutate Torch state. A thread-safe collection does not make the game state stored in it safe to mutate. Possessing an entity, inventory, world, chunk, or block reference does not grant permission to mutate it.

## 28.2 Deadlock prevention is an API requirement

Do not expose ordinary gameplay methods that secretly perform blocking cross-owner calls. In particular, an owner must not synchronously wait for work whose completion requires another owner or the same bounded simulation pool to make progress.

Prohibit, or explicitly detect and reject, patterns such as:

- owner A submits work to owner B and blocks waiting for the result while B waits for A;
- a callback waits on a future, latch, monitor, or task queued behind itself;
- a worker blocks waiting for work scheduled onto the same saturated bounded pool;
- plugin code performs a synchronous cross-owner operation while holding a lock needed by the target owner;
- lifecycle shutdown waits for a callback or task that is itself waiting for shutdown to complete;
- nested event dispatch or reentrant API calls create a dependency cycle.

Timeouts can limit how long a caller waits; they do not make a cyclic dependency correct. Do not use timeouts as the primary deadlock strategy.

The default cross-owner API should offer explicit nonblocking request/command operations with completion stages, cancellation, deadlines where meaningful, and documented failure/stale-result behavior. Completion callbacks must not run on an arbitrary simulation owner unless that execution context is explicitly part of the contract. Provide owner-local synchronous operations only when the caller is already in the correct validated context and the operation is genuinely local.

Where a multi-owner operation must appear atomic to gameplay, define a dedicated protocol (for example, prepare/validate/commit with deterministic ordering or a single designated authority). Do not implement atomicity by blocking owners in a cycle.

Development diagnostics should detect suspicious blocking from simulation contexts where practical. Provide useful reports containing the plugin, task/callback, source owner, target owner, wait dependency, and duration. Avoid false claims that every arbitrary Java-level deadlock can be detected or prevented.

## 28.3 Data-race prevention and authority enforcement

Every public operation that touches live mutable state must state and enforce one of these contracts:

- **Owner-only:** legal only while executing in the authoritative owner's validated context.
- **Snapshot:** returns immutable or safely published data with a documented consistency/version guarantee.
- **Command/request:** submits a mutation request to the authoritative owner. A particular request may be rejected, delayed, cancelled, or found stale when its actual preconditions require that outcome. This does not make the underlying capability unavailable: Torch must provide a documented way to invoke every meaningful native capability through a valid execution path, including owner routing or a coordinated protocol where required. A rejection is an operation result, not an acceptable substitute for implementing the capability.
- **Explicit concurrent contract:** safe from multiple contexts because its synchronization, conflict behavior, and consistency model are deliberately specified and tested.

Do not leave the threading contract unspecified.

Live mutable engine objects must not expose setters or mutable collections that bypass owner checks. Handles/facades may resolve the current authoritative object and validate lifecycle, owner, and generation, but they must not omit meaningful engine operations available in the underlying subsystem. The native API must expose those operations through appropriate owner-aware methods, commands, snapshots, or coordinated protocols. A handle is not a lock and is not proof that its target remains valid. Enforcing execution rules determines how a capability is accessed, never whether Torch exposes that capability.

Owner assertions must check logical owner identity and generation, not just Java thread identity. Enforce them at the mutation boundary, not only in optional convenience wrappers. In development/test builds, illegal mutation should fail loudly with actionable context. Production behavior must be deliberate, observable, and documented; silently ignoring an illegal mutation is not an acceptable default.

For cross-owner work, carry the minimum immutable data needed to express the intent. Validate target lifecycle, owner, generation, relevant state version, permissions, and gameplay preconditions at commit time. A check performed before an asynchronous delay is not sufficient. Define idempotency or duplicate detection for requests that may be retried.

## 28.4 Events, hooks, ordering, and reentrancy

Every event/hook family must document:

- which owner or coordinator dispatches it;
- whether it is synchronous, asynchronous, or split into phases;
- the state that listeners may read or mutate;
- listener ordering and priority semantics;
- whether cancellation is supported and the exact point at which cancellation remains effective;
- whether nested dispatch/reentrant calls are permitted;
- how listener exceptions are isolated and reported;
- whether dispatch can cross an owner boundary;
- what happens if the target entity/world/plugin is removed or migrated during dispatch.

Do not change a historically synchronous event into an asynchronous event merely to increase throughput. That can change observable gameplay ordering and break plugins. Where asynchronous observation is useful, provide a distinct API with explicit snapshot semantics instead of silently changing the original event contract.

Do not hold engine-wide locks while invoking arbitrary plugin callbacks. Do not call plugin code from partially committed state unless the event contract explicitly defines that phase and all invariants remain valid. Avoid invoking callbacks while holding locks that the callback could indirectly reacquire. Reentrancy must either be supported with defined invariants or rejected with a clear diagnostic; it must not be accidental.

Events that affect multiple owners require an explicit protocol. Define whether the event is local, coordinated, or observational; do not broadcast mutable live objects to listeners running concurrently on different owners.

## 28.5 Plugin lifecycle and owned resources

Plugin lifecycle must be a state machine with explicit transitions, at minimum:

`DISCOVERED → LOADED → ENABLING → ENABLED → DISABLING → DISABLED → UNLOADED`

Failure transitions must be defined. A plugin that fails during enable must not be treated as fully enabled; partial registrations and resources must be rolled back or tracked for cleanup.

Every plugin-owned resource must be registered with a lifecycle owner or resource scope. This includes event listeners, scheduled tasks, repeating/delayed jobs, commands, hooks, executor submissions, subscriptions, network handlers, metrics, temporary state, and compatibility-layer registrations. Disabling/unloading a plugin must prevent new work from being admitted and cancel or invalidate outstanding work according to its contract.

Cancellation alone is not proof that a running callback has stopped. Define how disable behaves when callbacks are already executing: cooperative cancellation, bounded draining, invalidation of late results, and a documented policy for work that does not stop. Do not permit a late task to mutate state after its plugin has been disabled or its target generation has changed.

Classloader unloading is best-effort and requires releasing references held by threads, static registries, callbacks, thread context classloaders, and engine-owned resource tables. Do not claim a plugin is unloaded merely because its lifecycle method returned.

Define reload semantics separately from disable/enable. Reload must not create duplicate listeners, tasks, commands, or classloaders, and must not leave two plugin generations concurrently controlling the same resource unless an explicit handover protocol permits it.

## 28.6 Plugin-created concurrency and shared resources

Document what Torch guarantees about plugin code and what remains the plugin author's responsibility.

- Plugins may use their own executors for independent work, but must not use those executors as a route around Torch's ownership rules.
- Prefer Torch-managed bounded executors or explicit task APIs for CPU work and blocking I/O so resource usage can be measured and admission-controlled.
- Do not run arbitrary blocking plugin code on simulation workers.
- Do not allow one plugin to monopolize shared execution capacity without quotas, backpressure, or diagnostics.
- Shared plugin data remains the plugin's responsibility unless Torch provides a specific concurrent data abstraction.
- Thread context, permissions, tracing context, and plugin identity must be propagated deliberately across supported asynchronous boundaries.
- Exceptions must be attributed to the responsible plugin/task and must not silently corrupt owner scheduling or terminate unrelated owners.

Torch cannot guarantee safety against arbitrary plugin code that deliberately mutates internals through reflection, unsafe operations, native code, or leaked implementation references. A Java plugin API is not a security sandbox. Reduce accidental violations through API boundaries and enforcement; treat hostile-code isolation as a separate process/security problem.

## 28.7 Compatibility plugins and legacy main-thread assumptions

The future Bukkit/Spigot/Paper compatibility layer must explicitly translate legacy scheduling and event assumptions. Do not map every legacy synchronous callback to an arbitrary owner worker.

Inventory compatibility requirements for each supported API include:

- main-thread checks and `isPrimaryThread`-style assumptions;
- synchronous task scheduling and repeating-task order;
- asynchronous task restrictions;
- world/entity/block/inventory access from legacy async tasks;
- event priority, cancellation, and reentrancy;
- plugin disable cancellation and task cleanup;
- calls that synchronously wait for world state;
- callbacks that expect immediate mutation visibility.

Preserve legacy synchronous semantics where required by the compatibility contract, even if the implementation uses a coordinator or owner-routing mechanism internally. If a specific legacy operation cannot preserve its expected semantics, document the exact compatibility limitation and provide a deliberate alternative; do not silently weaken ordering or introduce a blocking cross-owner call.

A limitation in the Bukkit/Spigot/Paper compatibility adapter must never become a limitation in Torch's native API. Native Torch APIs must expose the underlying engine capability through a valid owner-aware or coordinated path even when legacy semantics cannot be reproduced exactly. Compatibility constraints govern the adapter, not the native engine's capability surface.

## 28.8 Required adversarial tests

Add repeatable tests for these cases before claiming plugin concurrency is safe:

1. **Reciprocal owner requests:** owner A requests B while B requests A; neither owner may block the progress required by the other.
2. **Same-pool self-wait:** a task waits for work queued behind itself; detect/reject the invalid wait or prove the scheduler contract makes it impossible.
3. **Wrong-owner mutation:** a plugin attempts to mutate an entity, block, or inventory outside its current authority; the operation must be rejected or explicitly routed.
4. **Stale async result:** pathfinding/AI or plugin computation completes after movement, migration, removal, reload, or generation change; it must not commit stale state.
5. **Migration during callback/task:** queued and running work must have deterministic, documented outcomes and must not create two writers.
6. **Disable during execution:** disable a plugin while a callback, delayed task, or async computation is active; late results must be invalidated and resources cleaned up.
7. **Reentrant event:** a listener triggers an operation that dispatches the same or a dependent event; behavior must be defined and must not deadlock or corrupt partial state.
8. **Exception isolation:** a listener/task throws; owner progress, other plugins, and cleanup must follow the documented failure policy.
9. **Queue saturation and noisy plugin:** a plugin floods tasks or blocks its own executor; unrelated owners must retain progress and overload must be observable.
10. **Blocking I/O pressure:** slow database/HTTP/filesystem calls must not consume simulation-worker capacity.
11. **Cross-owner transaction:** hoppers, pistons, damage, projectiles, and inventories must not duplicate, lose, or reorder authoritative state.
12. **Shutdown:** outstanding tasks, completions, and plugin disable hooks terminate or time out according to a documented policy without waiting in a dependency cycle.

Use deterministic test doubles where possible, repeated stress runs, randomized interleavings, bounded test timeouts, and reproducible traces. A stress test passing once is not proof of race freedom. Use targeted invariants and state-transition assertions as well.

## 28.9 Required observability

Provide or plan diagnostics that can answer:

- which plugin callback/task is running or blocked;
- which owner and generation it belongs to;
- whether it is allowed to mutate current state;
- queue depth, wait time, execution time, cancellation delay, and starvation;
- cross-owner request source, target, age, and completion/failure status;
- stale-result rejection counts;
- plugin task/listener/resource counts before and after disable/reload;
- repeated exceptions, timeouts, and suspected dependency cycles.

Tracing should correlate a gameplay operation across owner handoffs without requiring global blocking. Diagnostics must be bounded and configurable so observability itself does not become an unbounded memory or CPU cost.

## 28.10 Completion criteria

Do not declare the plugin concurrency architecture complete until:

- every public live-state API operation has an explicit execution/consistency contract;
- owner and generation enforcement occurs at authoritative mutation boundaries;
- ordinary cross-owner APIs do not hide blocking waits;
- event dispatch ordering, cancellation, exception, and reentrancy semantics are documented;
- plugin lifecycle owns and cleans up registrations and outstanding work;
- legacy main-thread assumptions have an explicit compatibility strategy;
- the adversarial tests above exist or each unavailable test is recorded as a concrete blocker;
- known limitations are stated honestly, including the fact that arbitrary plugin code is not sandboxed.

**Final plugin rule: complete meaningful engine access through the native API is mandatory. Ownership, concurrency, lifecycle, and consistency contracts govern how each capability is used; they must never be used as a reason to omit it. Rejecting an invalid operation is not the same as withholding its capability. Compatibility limitations stay within compatibility adapters. Implicit mutation authority, hidden blocking, undefined callback ordering, and unowned asynchronous work are not acceptable.**

Two production notes from the empirical audit ride in ADR-21: JLine's history attach is explicit (it does not happen at build), and requestShutdown interrupts the loop thread because terminal.close() alone does not unblock a pending read. Original proposal text follows.

**Original research notes (2026-10-18).** The concrete Torch baseline below was inspected in the develop code at commit 26851c46dd4bb6f9a931798146ad6056db275aa2. Paper source links that use main are floating references; resolve and record exact commits before implementation.

## 30.1 Existing Torch baseline

The current console is intentionally simple and lives at the launcher boundary:

- zamin-launcher/.../LauncherRuntime.java is the composition root. It reads System.in with a UTF-8 BufferedReader, prints > , dispatches stop/shutdown, save, and state, and sends ordinary slash commands to EngineServer.consoleCommand.
- zamin-launcher/.../ZaminLauncher.java configures java.util.logging.SimpleFormatter; the process logging API is JUL (java.util.logging), not Log4j2.
- LauncherRuntime.attachFileLogging writes logs/latest.log using a rotating JUL FileHandler (5 MB files, five generations). Console output and file output are currently coupled through JUL handlers rather than independent, declarative sinks.
- server/chat/CommandService is the command dispatcher: it parses the command name and arguments, enforces each command's operator level, returns the normal unknown-command refusal for both unknown and unauthorized commands, catches runtime failures, and records command result counts. ConsoleSender is level 4 and routes feedback through the logger. ConsoleCommandTest verifies that a bare console line reaches the same server-side command route and persists its effect.
- When input reaches EOF or the console throws an IOException, LauncherRuntime waits for server shutdown rather than stopping the server. Preserve this: losing an interactive terminal must not unexpectedly kill a running server.
- The engine already has ownership-bound simulation scheduling and a bounded blocking-I/O lane. The terminal reader must not become a simulation thread or receive live mutable world state.

The relevant current files are zamin-launcher/src/main/java/net/zaminmc/torch/launcher/LauncherRuntime.java, ZaminLauncher.java, zamin-core/src/main/java/net/zaminmc/torch/server/chat/CommandService.java, ConsoleSender.java, zamin-core/src/main/java/net/zaminmc/torch/server/concurrent/BlockingIoLane.java, and zamin-core/src/test/java/net/zaminmc/torch/server/ConsoleCommandTest.java.

## 30.2 What the upstream implementation actually does

Primary references examined:

- Paper's PaperConsole at [commit a90108f43cabdf058548f9b27b9319bf7842c49d](https://github.com/PaperMC/Paper/blob/a90108f43cabdf058548f9b27b9319bf7842c49d/paper-server/src/main/java/com/destroystokyo/paper/console/PaperConsole.java). It extends SimpleTerminalConsole; it is not a second command dispatcher.
- [TerminalConsoleAppender README](https://github.com/Minecrell/TerminalConsoleAppender/blob/master/README.md) and [TerminalConsoleAppender.java](https://github.com/Minecrell/TerminalConsoleAppender/blob/master/src/main/java/net/minecrell/terminalconsole/TerminalConsoleAppender.java), observed on master on 2026-10-18. Its documented artifact is net.minecrell:terminalconsoleappender:1.3.0; lock and review the actual selected dependency version before adopting it.
- [Paper's log4j2.xml](https://github.com/PaperMC/Paper/blob/main/paper-server/src/main/resources/log4j2.xml), observed on main on 2026-10-18.
- Paper's [BrigadierCommandCompleter](https://github.com/PaperMC/Paper/blob/main/paper-server/src/main/java/io/papermc/paper/console/BrigadierCommandCompleter.java) and [BrigadierConsoleParser](https://github.com/PaperMC/Paper/blob/main/paper-server/src/main/java/io/papermc/paper/console/BrigadierConsoleParser.java), observed on main on 2026-10-18.

Verified distinctions:

1. **JLine is the terminal interaction layer.** Its Terminal and LineReader provide line editing, a persistent editable input line, history, parser/completer hooks, and terminal-aware output. Terminal detection matters: redirected stdout or a hosting panel may not support the same features as a real TTY. ANSI support is a separate capability and must also be detected/overridden deliberately.
2. **TerminalConsoleAppender is a Log4j2 output appender, not the command system.** It prints through a JLine terminal and, when the reader is attached to that terminal, can redraw the prompt/input line after log output. The appender's SimpleTerminalConsole is a reference input-loop abstraction; an application must still provide command dispatch and shutdown. The upstream README advises asynchronous logging because terminal writes can block.
3. **Paper wires several pieces together.** PaperConsole connects the line-reading abstraction to the server's command path; Paper's parser/completer bridge the console cursor to Brigadier. The log4j2.xml config separately defines a TerminalConsole, a file appender rolling logs/latest.log into dated compressed logs, and asynchronous fan-out. The file layout strips ANSI formatting. Its NETWORK_PACKETS marker filter is a logging filter, not a terminal feature.
4. **Completion can touch server-owned state.** Paper's completer parses command input and schedules suggestion computation through the main server executor before joining the result. That behavior is evidence of a threading boundary, not a recipe to copy unchanged. A join/wait that can deadlock or stall Torch's owner thread is unacceptable.
5. **Licensing and backend differ.** TerminalConsoleAppender is documented as a Log4j2 appender and its README identifies its license. Torch currently uses JUL and has no established Log4j2 configuration. Adding the appender alone would not transparently integrate with the current logger; switching logging backends is a separate architectural and dependency decision.

## 30.3 Torch decision

**Use JLine 3 directly behind a small Torch terminal adapter, and retain JUL as the logging source of truth for the first implementation.** Do not adopt TerminalConsoleAppender until an explicit logging-backend decision says Torch is moving to Log4j2. This gets the user-facing capabilities without introducing two logging systems or creating a parallel command route.

The terminal adapter belongs at the launcher/integration boundary. It owns only terminal I/O, rendering, history, and completion presentation. It does not own server lifecycle state, command parsing/execution, permissions, world state, or logging retention. Do not add a wrapper/module merely to mirror Paper's class names.

Implement the following:

- **Input and redraw:** create one JLine Terminal and LineReader for the interactive session. Route log messages through a JLine-aware JUL Handler/writer that prints above the currently edited line and restores the prompt and buffer. Never interleave raw System.out.println calls with JLine-managed input once interactive mode is active.
- **One command path:** once a line is accepted, pass it to the existing EngineServer.consoleCommand/CommandService route. Keep aliases, command-result recording, permission refusal, plugin/native registration, exception handling, and stop/save behavior in that route. Do not introduce a console-only command registry or bypass operator level checks.
- **Completion:** use the existing command-service registry as the semantic source of truth. Add a completion/query surface that emits immutable candidates from a safely published registry snapshot. If completion requires dynamic game state, capture only the necessary immutable facts on the authoritative owner and publish/version the snapshot; compute candidate formatting on the console thread. Never provide a live world/player/entity reference to the completer. Never hold up a tick waiting for console completion, and never make tab completion a synchronous cross-owner RPC. Plugin registration/unregistration must invalidate or rebuild the snapshot.
- **History:** configure bounded persistent history; make its location and limits explicit; exclude commands designated sensitive by policy and avoid storing credentials/tokens. History persistence errors must not crash the server or leak the entered command into another output sink.
- **Terminal and ANSI detection:** support auto, forced on, and forced off only as deliberate operator choices. Default to automatic capability detection. If the environment is non-interactive, unsupported, redirected, or a control panel, turn off line redraw and ANSI escapes and use a plain line-oriented mode when input is available. If stdin is absent or closes, disable the reader and leave the server running.
- **Formatting:** timestamps, levels, logger/source, message text, and complete exception details must survive. Color is presentation only: colorized terminal messages must retain the same semantic content as the file record; the file must contain no ANSI escape sequences. Minecraft legacy formatting codes need a documented strip-or-translate rule rather than passing raw control codes to every terminal.
- **Output policy:** route the same log event to independent terminal and file sinks. A terminal level/filter may hide noisy output from the screen but must never discard that record from the persistent diagnostic sink. Preserve an asynchronous or bounded handoff for potentially slow terminal/file I/O; define what happens when a sink queue is full.
- **Lifecycle:** the reader runs outside the simulation/owner thread. stop, shutdown, Ctrl+C, JVM shutdown, terminal EOF, and terminal failure converge on idempotent lifecycle operations. Stop accepting lines when shutdown begins; unblock/close the reader, then join its thread with a bounded deadline. Do not wait for a terminal thread while holding an owner gate or while a tick is required for shutdown progress.
- **Errors:** a failed JLine initialization should log the reason, disable enhanced mode, and fall back to plain I/O where practical. A broken command, completion error, terminal write failure, or history failure must be isolated from the simulation loop. Do not swallow the main failure silently.
- **Configuration:** the proposed tweaks/console.yml is an architecture-level configuration target, not an existing file. It should control interactive-mode selection, ANSI policy, prompt, history enablement/path/limit/sensitive-command policy, completion mode, terminal log threshold, and fallback behavior. Keep persistent logging level/rotation/retention under logging configuration rather than making console visibility decide what gets saved. Do not create that file as part of this documentation-only change.
- **Dependencies:** use the JLine terminal and reader artifacts at one aligned version; select exactly one terminal provider (Jansi or JNA) after Windows/Linux/macOS and packaged-runtime checks. Pin versions centrally, check transitive dependencies and license notices, and verify the release artifact contains the required providers. Do not copy a dependency version merely because an upstream sample uses it.

Do not expose a new Console API simply to reproduce JLine types. If a native plugin capability is needed, expose documented server-console/command-completion contracts through the existing native API architecture, independent of JLine implementation details. No public method may bypass §27.6 ownership rules.

## 30.4 Configuration semantics and tests

The configuration must have documented auto behavior and startup diagnostics for each branch. An explicit on request that cannot be honored should warn and fall back safely rather than printing escape sequences blindly. off must disable interactive editing/colors without disabling command dispatch where a plain input stream exists. Terminal output and file-log thresholds are independent.

Required tests before this proposal can be marked implemented/verified:

1. A real command typed through the interactive reader takes the existing command route and retains permission/result behavior.
2. A log record emitted while a partially typed command is present redraws cleanly, preserving both the line and cursor; concurrent log bursts do not scramble or lose terminal output.
3. History survives restart, remains bounded, handles unreadable/locked history files, and excludes configured sensitive commands.
4. Completion works for built-in and registered plugin/native commands; unknown, partial, mid-line cursor, and argument candidates are tested. A deliberately slow owner must not be stalled by completion, and completion must not return a stale mutable-world answer as authoritative.
5. TTY auto-detection, redirected streams, no stdin, EOF, unavailable terminal providers, ANSI forced off/on, and plain-console fallback are covered.
6. Shutdown by command, Ctrl+C, signal hook, EOF, terminal exception, and repeated shutdown is idempotent; the input thread does not keep a stopped process alive.
7. Terminal filtering never removes a record from the file sink; file output strips ANSI and preserves full exceptions; rotation and backpressure behavior are tested.
8. The same tests run against the packaged server artifact, not only the Gradle test classpath.

**Acceptance gate:** no production console claim until the terminal adapter, JUL bridge, completion snapshot, fallback, lifecycle tests, and packaged-runtime checks pass. This section is a design plan, not evidence that any of those changes have landed.

# 31. WORLD STORAGE LAYOUT — VANILLA/PAPER 26.1+ REFERENCE, TORCH FORMAT BOUNDARY

**Status: TARGET ARCHITECTURE — the modern backend remains future-gated (§31.4's own decision: the current Torch format stays the default until codecs, round trips, and crash-recovery tests exist). The IMMEDIATE boundary items LANDED on develop (2026-10-19): WorldSessionLock (§31.6 session ownership — an OS FileLock over world/session.lock held for the whole run and released at shutdown; a crashed process's lock evaporates with it so there is no stale-marker recovery to get wrong, and a genuinely live second writer is refused loudly BEFORE any store is touched) and StorageManifest (§31.4.5 format identity — world/data/storage.properties carrying the format family and layout generation independent of the game version: first boot writes it, every boot verifies it, a different family or a NEWER layout refuses to touch the world — the no-implicit-conversion guard). StorageBoundaryTest 8 (the lock's refusal/release/stale-marker/no-contention arms; the manifest's first-boot/wrong-family/newer-layout/garbage/unreadable arms; the real two-boot restart walk). The modern 26.1 backend itself, the codecs, and the migration machinery remain future slices under §31.7's contract.** Research checked on 2026-10-18. The Minecraft 26.1 format and Paper 26.1 migration rules below are based on official public documentation. Paper source links that use main were inspected on that date and must be pinned to a commit before implementation.

## 31.1 Existing Torch storage is not a Vanilla 26.1 world

Current Torch has server/config/ServerLayout, EngineConfig.worldDir(), worldDataDir() and playerDataDir(), plus the WorldStorage abstraction and custom DeltaWorldStorage implementation. The current layout is a Paper-like server home with a world folder, world/data, and world/playerdata; the main world persistence abstraction saves a Torch delta snapshot in a Torch-owned binary format. Numerous separate engine stores persist entity, player, block-entity, and subsystem state. That is **not** a Minecraft 26.1 level.dat/Anvil-world implementation and must not be labelled Vanilla/Paper-compatible because the folder names look similar.

Relevant code inspected:

- zamin-core/src/main/java/net/zaminmc/torch/server/config/EngineConfig.java
- zamin-core/src/main/java/net/zaminmc/torch/server/config/ServerLayout.java
- zamin-core/src/main/java/net/zaminmc/torch/server/world/WorldStorage.java
- zamin-core/src/main/java/net/zaminmc/torch/server/world/DeltaWorldStorage.java
- zamin-core/src/main/java/net/zaminmc/torch/server/concurrent/BlockingIoLane.java
- per-subsystem *DataStore classes and their versioned readers/writers.

Torch's 1.8.8 gameplay target, current custom serialized records, legacy block/item identifiers, and versioned Torch save formats remain separate from a modern Vanilla file layout. A 26.1 folder migration also changes serialized data, names and metadata semantics; moving folders alone does not convert those contents.

## 31.2 Verified Vanilla 26.1+ layout

Primary sources:

- Mojang's [Minecraft Java Edition 26.1 release notes — World Storage](https://feedback.minecraft.net/hc/en-us/articles/44551668333837-Minecraft-Java-Edition-26-1).
- Paper's [26.1 update announcement](https://papermc.io/news/26-1/), published 2026-04-26.
- Paper's [migration guide](https://docs.papermc.io/paper/migration/) and [world configuration guide](https://docs.papermc.io/paper/reference/world-configuration/).
- Paper's live migration implementation: [WorldFolderMigration](https://github.com/PaperMC/Paper/blob/main/paper-server/src/main/java/io/papermc/paper/world/migration/WorldFolderMigration.java), [WorldMigrationSupport](https://github.com/PaperMC/Paper/blob/main/paper-server/src/main/java/io/papermc/paper/world/migration/WorldMigrationSupport.java), [VanillaWorldMigration](https://github.com/PaperMC/Paper/blob/main/paper-server/src/main/java/io/papermc/paper/world/migration/VanillaWorldMigration.java), and [LegacyCraftBukkitWorldMigration](https://github.com/PaperMC/Paper/blob/main/paper-server/src/main/java/io/papermc/paper/world/migration/LegacyCraftBukkitWorldMigration.java). These files were inspected on main on 2026-10-18; resolve the links to a full source commit before implementing a port.

The relevant modern structure is, conceptually:

~~~text
<world>/
├── level.dat
├── data/
│   └── <namespace>/
│       └── ...                 # data shared across dimensions
├── datapacks/
├── dimensions/
│   └── <namespace>/
│       └── <dimension-key>/
│           ├── data/
│           │   └── <namespace>/
│           │       └── ...     # data owned by this dimension
│           ├── entities/
│           ├── poi/
│           ├── region/
│           └── ...             # format/version-specific dimension files
├── players/
│   ├── advancements/
│   ├── data/
│   └── stats/
├── resourcepacks/
│   └── resources.zip           # optional world resource pack
└── generated/
    └── <namespace>/
        └── structure/          # saved structure-block templates
~~~

Details relevant to a faithful implementation:

- The default dimensions use keys minecraft:overworld, minecraft:the_nether, and minecraft:the_end, stored beneath dimensions/minecraft/overworld, dimensions/minecraft/the_nether, and dimensions/minecraft/the_end. The folder scheme is keyed by namespace and dimension path, not the server's display/world name.
- The root data/ is now for data shared between dimensions. Dimension-owned data moves under the matching dimension's data/. Vanilla saved-data files live under namespace subdirectories: for example, data/minecraft/scoreboard.dat; command storage uses data/<namespace>/command_storage.dat.
- Mojang's 26.1 notes also record file/name changes including chunks.dat → chunk_tickets.dat, maps under data/minecraft/maps with numeric filenames, idcounts.dat → last_id.dat, removal of the special raids_end.dat name, and generated/<namespace>/structure (singular). These are format semantics, not cosmetic examples; any actual converter must enumerate all rows for the target version.
- Player directories are under players/: advancements, data (player saves), and stats. resources.zip, when used, is under resourcepacks/.
- level.dat itself also changed: 26.1 replaces the legacy Player tag with singleplayer_uuid and changes difficulty settings, among other versioned data changes. A folder migration must not pretend to implement those tag/data-version conversions.

The list above is a high-level directory contract from the 26.1 release notes, not a replacement for the selected Minecraft version's full storage API, datafixers, or per-file schema. Recheck the official release notes and source on every game-version upgrade.

## 31.3 Paper-specific behavior is not Vanilla format

Paper 26.1 follows the new dimension-based structure while preserving per-world settings that were historically coupled to the Bukkit storage layout:

- Per-world configuration is stored beside each dimension as dimensions/<namespace>/<key>/paper-world.yml; defaults live under config/paper-world-defaults.yml. The per-world file contains only overrides and inherits defaults. It is **Paper-owned config**, not a Vanilla world file.
- Paper-only state is kept under the dimension's namespaced data, e.g. dimensions/<namespace>/<key>/data/paper/level_overrides.dat, metadata.dat, and persistent_data_container.dat. Do not write Torch-owned data into the paper namespace.
- Paper preserves dimension/world identity, gamerules, spawn/level overrides, PDC, and related saved data during migration. Its implementation moves eligible legacy dimension directories (region, entities, poi), migrates per-world config when a target config is absent, handles shared saved-data rows, and imports legacy Paper/CraftBukkit metadata. Some of its routines delete migrated legacy roots only after the migration path completes.
- Paper's world-key direction is also important: a name is a display/configuration selector, while a stable namespaced key identifies the world/dimension. Paper states that direct Spigot/CraftBukkit → Paper 26.1 migration is fundamentally unsupported; the documented route goes through Vanilla first. Do not claim that a legacy directory layout can always be transformed safely.

Torch should adopt the identity, separation, and namespace principles, not Paper-owned filenames or Paper's implementation as a drop-in converter.

## 31.4 Explicit Torch format decision

1. **Supported format today:** the current Torch custom persistence format and current Torch/Paper-like runtime directory organization only. Vanilla 1.8.8 Anvil/level.dat imports, Bukkit multi-folder worlds, and Vanilla/Paper 26.1 files are not currently verified import formats.
2. **Modern layout decision:** treat the Vanilla 26.1+ dimension/namespace layout as a **future versioned storage backend and migration target**, not as a live default or a claim about today's new-world saves. Keep the present backend selected by default until the new backend's codecs, save/load round trips, all *DataStore mappings, and crash-recovery tests exist. A later decision may make it the default for new worlds only after the implementation preserves all required Torch state and declares exactly which game-data format it writes.
3. **No implicit conversion:** never detect an old layout and silently convert it during normal startup. Never read a 1.8.8 save as a 26.1 save because both have a world/ directory. An explicit migration command should be a separate maintenance operation with a dry-run report, a full backup, and a declared source and target format.
4. **No format overclaim:** a modern directory tree alone does not make chunk data, level.dat, saved data, player files, IDs, NBT, entity records, POI, or data packs compatible with Vanilla 26.1. Likewise, porting a modern path shape does not change Torch's gameplay target from 1.8.8.
5. **Version and identity markers:** every backend needs a stable format identifier and monotonically versioned schema. Store Torch metadata under a Torch-owned namespace, such as data/torch/ or dimension-local data/torch/, never under data/paper/. Record storage-layout version independently from gameplay/protocol version and independently from each subsystem's data schema. Unknown newer versions must fail safely or open read-only; never rewrite them using defaults.

This is deliberately conservative because WorldStorage currently loads/saves Torch snapshots, and no complete source-format converter was found in the inspected repository. It is not permission to reduce the API or to defer the public storage abstraction: the native API must expose supported world/dimension/storage capabilities as specified in §27 without leaking paths or raw mutable engine state.

## 31.5 Proposed Torch ownership and directory contract

The world name selects a root directory, but is not a dimension identity. Each world has a stable world ID; each dimension is identified by a validated namespaced Identifier such as minecraft:overworld. A dimension key must not be derived from an unchecked path or a human display name. Identifier normalization and validation must reject empty, traversal, separator, absolute-path, and drive-prefix attacks before any filesystem resolution.

When the modern backend is implemented, use the following contract:

- **World-shared files:** <world>/level.dat and <world>/data/<namespace>/... only for fields that are truly shared across dimensions. Torch-global world-owned data, if needed, resides in the reserved torch namespace. Do not mix overworld-only weather, generators, or per-dimension block state into this shared store unless the selected game-version semantics say it is shared.
- **Dimension files:** <world>/dimensions/<namespace>/<dimension-path>/region, entities, poi, and <world>/dimensions/<namespace>/<dimension-path>/data/<namespace>/.... Each subsystem's save codec declares whether its data is world-shared, dimension-scoped, player-scoped, or global-server-scoped. Dimension paths are generated from validated IDs, not accepted as arbitrary input.
- **Per-dimension configuration:** keep defaults centrally (proposed config/torch-world-defaults.yml) and sparse per-dimension overrides in a clearly Torch-owned file beside the dimension (proposed torch-world.yml). These are Torch design names, not Vanilla/Paper standard files. Configuration is not saved world state; changes to defaults must not overwrite explicit dimension overrides.
- **Player data:** the modern-layout backend uses the corresponding players/data, players/advancements, and players/stats partitions only when the respective player schemas are implemented. Until then, keep the live Torch store unchanged. Player UUID is the persistence key; player name is metadata and must not decide file identity.
- **World generation and datapacks:** datapacks/ and generated/<namespace>/structure/ are format-specific surfaces. Only expose them as supported when pack validation, deterministic world-generation inputs, structure codecs, and their data-version behavior are implemented. A directory's presence alone does not establish support.
- **Other subsystem data:** do not merge all *DataStore files into one opaque blob simply to fit the tree. Inventory each store; record its owner scope, codec/schema version, atomicity, restore order, and migration transform. Preserve separate stores when they have independent lifecycle or update cadence.
- **World identity:** preserve stable world IDs across renames/moves and use dimension keys for dimension identity. Resolve multiple world roots deterministically and reject duplicate IDs rather than silently loading two copies of one world's state.
- **Public API boundary:** storage paths, manifests, codecs, locks and migration machinery are engine concerns. Native APIs expose typed storage capabilities and safe snapshots/operations; do not expose the underlying filesystem path as a substitute for a supported world API. Maintain Section 27's full-capability goal without bypassing owner authorization.

Do not create a new module or class for every individual file. Add the smallest storage-format adapter that gives WorldStorage an explicit codec/layout boundary and keeps authoritative world state independent of the on-disk representation.

## 31.6 I/O, concurrency, locking, and durability

- **Single writer:** at any instant there must be one authoritative writer for a given world/dimension/chunk or region file. Shared collections are not proof that the mutable values are safe to write concurrently.
- **Snapshot before I/O:** capture a consistent immutable snapshot under the correct ownership context; serialize/flush it on the bounded I/O lane. The worker receives no live mutable world/chunk/entity object and no mutation authority.
- **Stale-write prevention:** attach monotonically increasing save generation/revision metadata. A late completion from an older snapshot must not replace newer persisted state. Cancellation, unload, ownership migration, restart and server shutdown all invalidate or drain in-flight writes explicitly.
- **Atomic replacement:** where the filesystem supports it, write a sibling temporary file, flush file contents, and atomically replace the target. Document weaker guarantees on filesystems that do not support atomic moves. Never truncate the only known-good copy before replacement is ready. Preserve/quarantine corrupt inputs with a diagnostic rather than silently replacing them with an empty world.
- **Region I/O:** if using Anvil region files, serialize access per region file and use a bounded I/O pipeline. Do not let two workers update different chunks by concurrently rewriting the same region header/table. Keep chunk save scheduling, region-file locking and owner authority as separate but coordinated constraints.
- **Session ownership:** acquire a process/world-session lock before writes begin. Reject a second live writer for the same world instead of relying only on a lock file's presence or timestamp. If matching a particular Vanilla/Paper on-disk lock convention, confirm its precise semantics in that version's source first; stale-lock recovery must be deliberate and testable.
- **Ordering and save barriers:** preserve per-key save order, define whether saveAllNow waits for all accepted writes to become durable, reject new writes after shutdown begins, drain or cancel outstanding I/O deterministically, then close storage. A completed save response must mean what its API documents—accepted, flushed, or durable—not an ambiguous mixture.
- **Crash handling:** quarantine unreadable records and surface the path, format version, and reason. Do not silently turn unreadable state into default state and later overwrite the evidence. Boot must identify incomplete migration/save journals and either resume safely or stop without destroying source data.
- **Diagnostics:** expose queue depth, write latency, failure counts, last successful save, stale completion counts and per-world/per-dimension errors. Metrics must not become unbounded labels keyed by arbitrary plugin/world input.

This extends the existing §9 ownership, §13 persistence, and §17 lifecycle rules. It does not establish a second storage authority or relax §3's single-writer invariants.

## 31.7 Migration policy — explicit, backed up, recoverable

Paper's 26.1 code is useful evidence of the actual migration complexity, but Torch must not blindly replicate its startup behavior. Paper warns operators and delays startup migration; its implementation distinguishes no-op/current data, Vanilla migration, and legacy CraftBukkit migration, moves eligible folders/configuration, converts selected saved data and metadata, and may remove migrated legacy roots at the end. Paper's own guide says Bukkit/CraftBukkit → Paper 26.1 cannot be a direct migration. These facts demonstrate that this operation is a format conversion with destructive risk, not a harmless directory tidy-up.

Torch's migration contract:

1. **Preflight, no writes:** acquire exclusive maintenance ownership or require the server to be stopped; identify source/target backend and format versions; inspect every known file/store and data version; detect duplicate worlds/IDs, symlinks or path escape, incomplete prior runs, corrupt entries, free-space shortage, and destination collisions. Output a machine-readable and human-readable plan with counts, expected moves/conversions, omissions and risk.
2. **Explicit consent:** require an explicit operator command/flag. Never auto-convert because startup found a legacy layout. Never interpret --force as permission to overwrite unrecognized data.
3. **Backup:** require a full consistent backup made while source writers are stopped. Verify it is readable before touching source files. For the modern 26.1 target, record that Vanilla warns a world upgraded to 26.1 cannot be downgraded to older releases.
4. **Staging and journal:** write into a new staging destination, not over the source. Maintain a versioned journal of each action, source hash/identity, output, and completion state. Operations must be idempotent. Preserve unknown files unchanged unless a reviewed migration explicitly handles them.
5. **Conflict rule:** do not overwrite a target just because a source has the same basename. If both source and target exist with conflicting content, stop and report; provide a separate, explicit resolution tool rather than choosing silently.
6. **Validated transforms:** directory moves and file-format transformations are separately enumerated. For each field, map what happens to level metadata, shared/per-dimension saved data, blocks/chunks, block entities, entities, POI, players, scoreboard, stats, advancements, datapacks, generated structures, Torch stores, and plugin/native data. If any required row lacks a converter, mark that source format unsupported rather than claiming a complete migration.
7. **Verification before cutover:** reopen the staged destination through the target reader; verify file inventories, per-store counts, checksums where meaningful, owner UUIDs, dimension IDs, and representative chunk/entity/player round trips. Compare gameplay invariants when the source semantics can be represented. A matching file count alone is insufficient.
8. **Atomic cutover and recovery:** keep the original source untouched until validation passes. Promote the staged tree through a documented rename/swap mechanism where supported. If cutover fails, restore the prior active root. Retain backup, journal, source and report until the operator explicitly confirms cleanup.
9. **Restart and observability:** report source and destination formats, converted/skipped/quarantined counts, every limitation and warning. Startup detects an interrupted journal and refuses normal writes until recovery is resolved; it must not repeatedly apply a partial migration on every boot.
10. **Compatibility boundary:** do not claim a direct import from a legacy Bukkit/Paper 1.8.8 folder into the Vanilla/Paper 26.1 data schema until a field-complete migration exists and passes tests. Paper's documented route for its own Bukkit-derived layout goes through Vanilla, but that is not automatically a valid converter for Torch's custom WorldStorage.

## 31.8 Storage tests required before declaring the modern backend supported

- New world and each default/custom dimension create the exact expected directory identities without path traversal or accidental key collisions.
- World-shared versus dimension-local saved data remains separate across save/reload and two dimensions with different values.
- Every WorldStorage and *DataStore schema has round-trip, absent-field, older-version, unknown-newer-version, malformed-input, truncation, and quarantine tests.
- Player UUID persistence survives player rename; modern player-file partitions are not written until their target codecs are implemented.
- Concurrent chunk/region writes cannot overwrite newer revisions; same-region writes serialize; separate regions may proceed only within the bounded I/O design.
- Fault injection covers crashes before temporary-file completion, after flush, during atomic replace, after journal update, and during migration cutover. Recovery preserves the only good source.
- Duplicate process/session access is rejected; shutdown/save barriers wait for the documented durability point; late stale completions do not reappear after unload or migration.
- Migration tests cover already-modern/no-op input, each supported legacy source, duplicate/colliding targets, symlinks/path escape, corrupt files, insufficient space, interrupted phases, backup validation, exact rollback, unknown files, and incomplete converter mappings.
- Golden fixtures from the targeted upstream release verify the actual directory names and codec/file semantics. Keep fixtures/version identifiers pinned; do not use the latest format fixture to infer an older version.
- The complete engine, native API, persistence, protocol, and real-client regression suites must remain green. Add before/after persistence correctness and I/O latency measurements, but do not claim speedups without reproducible workloads.

**Acceptance gate:** the modern layout is not supported until the backend can load, save, recover and migrate the complete declared source/destination formats. Until then, the existing Torch format remains the default and migration remains explicitly unsupported. The native API's capability goal in §27 is not reduced by this storage decision; it stays the obligation to expose all real supported capabilities through safe, documented contracts.
