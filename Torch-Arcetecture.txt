# TORCH — Permanent Concurrency Architecture
## Forensic Folia 26.2.x Analysis, Minestom Architecture Audit, and Multithreaded Engine Design

You are acting as the principal systems architect, JVM concurrency engineer, Minecraft server engineer, and code archaeologist for **Torch**, an independent Minecraft Java server platform under the ZaminMC namespace.

This is a foundational architecture assignment. Your decisions will guide the engine for years. Treat correctness, maintainability, vanilla mechanics, compatibility, and measurable performance as equally important engineering requirements.

Do not reduce this assignment to adding an executor, increasing a thread count, or copying Folia's region scheduler.

Your task is to understand the actual codebase, investigate Folia's implementation in the supplied `Folia-ver-26.2.x.zip` (https://github.com/ZaminMC/ZaminTorch/blob/develop/Folia-ver-26.2.x.zip), investigate the exact Minestom version Torch uses, and produce Torch's permanent concurrency architecture.

**This phase is architecture and documentation only. Do not begin the implementation until the architecture has been reviewed and approved.**

---

# 1. Mission

Design a concurrency architecture for Torch that can exploit multiple CPU cores safely and efficiently while preserving Minecraft gameplay semantics.

Torch must not inherit a universal single-thread assumption. It must also not replace that assumption with unrestricted concurrent access to mutable world state.

The architecture must establish:

- Who owns every category of mutable game state.
- Which thread contexts may read, calculate, and mutate that state.
- How simulation work is scheduled, balanced, migrated, and cancelled.
- How entities, blocks, chunks, redstone, physics, AI, and other systems interact across ownership boundaries.
- How expensive work can execute in parallel without allowing workers to corrupt authoritative game state.
- How heavily populated areas can use multiple cores without simply moving the single-thread bottleneck to a smaller region.
- How global state and operations that affect multiple owners are coordinated.
- How plugins, network events, persistence, world generation, and administration interact with the concurrency model.
- How correctness is enforced, tested, measured, and maintained as the engine grows.

The intended result is a documented, enforceable architecture that later implementation work can follow without repeatedly reinventing threading decisions.

## The central objective

Design Torch around **explicit state ownership, controlled mutation, parallel computation, and a scheduler that separates logical work from physical CPU threads**.

Treat this as a design principle, not an excuse to assume every Minecraft system can be parallelized independently.

A feature is not considered safely multithreaded merely because it runs on an executor.

Torch is independent server software. It is not a Folia fork, a Paper fork, or a project whose architecture should be defined by Bukkit compatibility.

Inspect the actual repository to establish precisely how Minestom is used, which modules Torch owns, which features are inherited, which features are customized, and which architectural assumptions already exist.

Do not assume Minestom's current threading implementation from memory or from an unrelated release. Identify the actual dependency version and inspect its matching implementation wherever possible.

Follow these constraints:

1. Do not copy Folia classes one-for-one or recreate its package structure under new names.
2. Do not introduce one permanent operating-system thread per world, region, chunk, entity, or player.
3. Do not make every field volatile, every collection concurrent, or every operation synchronized as a substitute for design.
4. Do not assume a `ConcurrentHashMap` makes the mutable objects stored inside it thread-safe.
5. Do not allow a worker to directly mutate state owned by another simulation owner.
6. Do not solve cross-owner interactions by routinely blocking one owner while waiting for another.
7. Do not force every game operation through one central coordinator.
8. Do not impose a global barrier on all world regions every tick without proving it is necessary and evaluating its scalability.
9. Do not silently drop vanilla behavior to avoid crossing an ownership boundary.
10. Do not claim Torch exceeds Folia simply because it uses a different algorithm or more worker threads.
11. Do not make speculative performance promises without measurements.
12. Do not add an elaborate concurrent framework where a smaller, provably correct mechanism is sufficient.

Torch should be designed to go beyond conventional region-based scheduling where the evidence justifies it. That ambition must never take priority over correctness.

# 6. Phase Three: define Torch's concurrency vocabulary

Before selecting algorithms or class designs, establish precise definitions.

The documentation must distinguish all of the following:

- **Physical worker:** an actual JVM execution thread.
- **Executor or worker pool:** the mechanism that runs eligible work.
- **Ownership domain:** the logical scope allowed to mutate a particular set of state.
- **Spatial partition:** a division of world space used to organize work and data.
- **Simulation task:** a unit of work that advances authoritative game state.
- **Compute task:** a unit of work that calculates a result without directly mutating authoritative state.
- **Service task:** I/O, persistence, compression, network handling, or another supporting operation.
- **Tick:** the logical progression of game simulation, which must not be confused with a worker task or a wall-clock timer.
- **Tick epoch:** a defined scheduling or coordination interval, if the selected architecture requires one.
- **Snapshot:** a consistent, explicitly bounded view of state made available for computation or observation.
- **Intent or command:** a proposed mutation that must be validated and applied by the appropriate owner.
- **Ownership token or execution context:** a verifiable indication that a task has permission to operate on a given scope.
- **Migration:** a controlled reassignment of ownership, state, or an entity between execution domains.
- **Cross-owner interaction:** an operation that reads from or affects state owned by more than one domain.

Define additional terminology when needed. Do not use “thread,” “region,” “worker,” and “owner” interchangeably.

Include a glossary and a set of invariants that every future contributor can understand.

# 7. Phase Four: propose the permanent architecture

Design Torch's architecture from the actual baseline and the Folia investigation.

The following are the minimum concepts that must be evaluated. They are requirements for the analysis, not permission to assume a particular implementation will work without proof.

## 7.1 Separate logical ownership from physical execution

Torch must have a clear distinction between:

1. The logical unit of mutable state.
2. The worker that executes an eligible task.
3. The pool or scheduling mechanism that supplies workers.
4. The lifecycle mechanism that transfers ownership.

A logical ownership domain should not depend on permanently owning one OS thread.

Evaluate a design in which eligible work can move between workers while ownership rules remain valid.

The architecture must answer:

- Can several independent owners progress simultaneously?
- Can a busy owner monopolize a worker indefinitely?
- Can an idle owner stop consuming tick resources?
- How can tasks be scheduled fairly?
- What happens when workloads change dramatically?
- How do we avoid excessive task creation, queueing overhead, and context switching?
- Which operations must remain serialized within an owner?
- What prevents two workers from executing conflicting writes to the same state?

Compare work stealing, work sharing, ready-task queues, partition-affine queues, and other plausible approaches against Torch's workload. Recommend the smallest system that satisfies the measured requirements.

Do not choose a scheduler merely because it is fashionable.

## 7.2 Establish one authoritative writer for mutable state

Define the authoritative owner for every important category of mutable state.

At minimum, provide an ownership table covering:

| State category | Required decision |
| --- | --- |
| Entity lifecycle and mutable entity state | Define owner and transfer semantics |
| Entity movement, collision, and damage | Define read/write ownership and interaction protocol |
| Chunk contents and block state | Define authoritative mutation ownership |
| Block entities and inventories | Define ownership and cross-boundary behavior |
| Neighbor updates and redstone state | Define ownership and propagation |
| Scheduled block and fluid ticks | Define scheduler ownership and ordering |
| Chunk membership and entity indexing | Define consistent publication and updates |
| Entity tracking and replication | Define authority and observation model |
| AI state and navigation | Define authoritative state versus off-thread calculation |
| Chunk loading and world generation | Define worker access limits and result publication |
| Lighting and derived chunk data | Define parallelism and invalidation |
| World metadata, time, weather, and game rules | Define global or partitioned ownership |
| Scoreboards, teams, and other global registries | Define concurrency and bottleneck strategy |
| Player inventory, menus, and player state | Define ownership during normal play and transfers |
| Plugin-owned data | Define guarantees and compatibility contract |
| Persistence and snapshots | Define consistency and save semantics |
| Network connections and packet state | Define event handoff and thread-safe output |
| Server lifecycle and configuration | Define the coordinator and shutdown model |

For each category, identify whether it is:

- Exclusively mutable by an owner.
- Immutable after publication.
- Concurrently readable under a defined rule.
- Modified through messages or intents.
- Coordinated by a transaction.
- Protected by a synchronization primitive, with justification.

Avoid unnecessary categories of unrestricted concurrent mutable state.

Ownership must be enforced in the design rather than existing only as documentation.

## 7.3 Define ownership enforcement

Design the mechanism by which the engine establishes and validates current ownership.

Consider:

- Ownership identities.
- Ownership generations or epochs.
- Current execution context.
- Entity and position ownership checks.
- Safe ownership transfer.
- Stale-task detection.
- Debug and production behavior.
- The overhead of checks in hot paths.

An old task must not gain access simply because it retained a reference after an ownership change.

Specify what happens when code accesses a resource it does not own. The default should be an explicit, diagnosable failure or a deliberate safe handoff, not silent corruption.

Do not invent a security guarantee from a Java object reference or a thread name.

The final architecture must clearly distinguish safe cross-thread observation from permission to mutate.

# 8. The key challenge: go beyond a simple regional tick scheduler

Torch's ambition is to use multicore hardware more effectively than a model that makes the entire heavily populated region one indivisible simulation job.

That does not mean splitting arbitrary Minecraft operations across threads and hoping they work.

Design and compare at least these levels of parallelism.

## Level A: independent ownership domains

Independent portions of the world can progress in parallel because each has its own mutable state and execution constraints.

This is the foundational model.

Specify the spatial partitioning scheme, its ownership boundaries, and how the scheduler discovers runnable work.

## Level B: parallel supporting computation

Move expensive calculations into appropriate worker pools where possible, including:

- Pathfinding.
- AI planning.
- Navigation calculations.
- Chunk generation.
- Structure generation.
- Lighting calculations.
- Serialization.
- Compression.
- Persistence preparation.
- Other demonstrably separable work.

Do not assume every named operation can immediately be moved off-thread. Identify its inputs, mutable dependencies, output, and publication protocol.

The worker should normally operate on a bounded snapshot or immutable inputs and return a result. The authoritative owner validates that result before applying any changes to live state.

## Level C: parallel work within a heavily loaded ownership domain

This is the critical research task.

A densely populated region can become a bottleneck if its entire simulation must execute serially.

Investigate whether Torch can safely parallelize selected work within one logical ownership domain through combinations of:

- Immutable snapshots.
- Read/write access declarations.
- Disjoint write sets.
- Independent entity calculations.
- Deferred mutation intents.
- Version validation.
- Conflict detection.
- Deterministic commit phases.
- Safe cancellation and recomputation.
- Bounded rebalancing of eligible tasks.

Do not assume these mechanisms are automatically sufficient.

For each candidate, explain how its algorithm interacts with the order-dependent nature of Minecraft simulation.

For example, two mob updates may independently calculate movement from the same snapshot but then attempt to occupy or collide with overlapping space. Two AI computations may have results based on a target that moved while the computation was running. A block update may invalidate a path, collision result, or redstone computation.

Your proposal must account for these conflicts.

### Required rule

**Parallel calculation does not grant parallel mutation rights.**

When an operation returns a result, its application must have a defined authority, validation rule, ordering rule, and failure behavior.

Compare at least two implementation strategies for heavy-domain parallelism:

1. Parallel computation with serialized authoritative mutation.
2. Conflict-aware parallel execution over genuinely independent mutable state.

Explain what each strategy can parallelize, what it cannot safely parallelize, and where its overhead becomes worthwhile.

If a proposed form of intra-domain parallelism cannot yet preserve the required gameplay semantics, classify it as future research rather than pretending it is solved.

Torch should first achieve a correct, measured foundation and expand the safe parallel execution surface incrementally.

# 9. Regionization and dynamic load balancing

Design how world space maps to logical ownership units.

Do not decide that a “region” must be a fixed collection of chunks merely because Folia uses regions.

Compare sensible models, including:

- Fixed-size spatial shards.
- Dynamically merged or split spatial domains.
- Chunk-based ownership.
- Region-based ownership.
- Hierarchical ownership in which coarse spatial partitions contain smaller independently scheduled tasks.
- Hybrid approaches.

Evaluate their memory overhead, scheduling overhead, load balance, boundary frequency, and gameplay correctness.

The design must explicitly answer:

- How is the initial ownership map built?
- How are chunks assigned to owners?
- How do entity ownership and chunk ownership interact?
- What happens near the boundary between domains?
- When is splitting useful?
- When is merging useful?
- What measurements justify a split or merge?
- How is oscillation between split and merge prevented?
- Can ownership change while tasks are queued?
- What happens to delayed work during migration?
- What happens to references or messages created under the old ownership generation?
- How are in-flight computation results invalidated?

The scheduler must be free to assign eligible work to different physical workers. However, no worker reassignment may violate logical ownership or create simultaneous conflicting writers.

Do not add dynamic region migration solely as a theoretical feature. Propose initial conservative behavior and define evidence-based conditions for enabling more aggressive balancing.

# 10. Cross-owner interaction protocol

This section is mandatory and central to the design.

Minecraft mechanics frequently involve multiple blocks, entities, chunks, and owners. A concurrency architecture that handles ordinary movement but fails on boundary interactions is not complete.

Define a common protocol for cross-owner requests and then specify where individual systems need stronger coordination.

## 10.1 General protocol

For a cross-owner operation, document:

1. The originating owner.
2. The target owner or owners.
3. The message or command being transferred.
4. The information included in the request.
5. The version or ownership generation against which it was created.
6. The validation performed by the receiving owner.
7. Who authorizes the mutation.
8. How the result returns to the initiating system.
9. What happens if the target changes state before the request arrives.
10. What happens if ownership changes while the operation is in flight.
11. How duplicate delivery is prevented or made harmless.
12. How failure, cancellation, and shutdown are handled.
13. How ordering guarantees are preserved.
14. How message queues and latency are bounded.

A one-way message should be the default when it can express the gameplay operation correctly.

Use asynchronous multi-owner coordination when atomicity genuinely requires it.

## 10.2 Hard prohibitions

Do not create routine dependency cycles in which owner A synchronously waits for owner B while owner B waits for owner A.

Do not block simulation workers on `Future.get()`, `join()`, latches, or locks whose progress depends on work running on the same saturated pool.

Do not perform implicit synchronous thread hopping deep inside common gameplay methods.

Do not assume a timeout means a gameplay transaction can simply be discarded.

Document how the system detects and avoids deadlocks, starvation, queue saturation, and transactions that are stuck waiting for an owner.

## 10.3 Required mechanics analysis

Specify ownership and boundary behavior for each of the following:

- Ordinary entity movement across a partition.
- Player movement and server-authoritative corrections.
- Entity collisions and knockback.
- Damage between entities in separate partitions.
- Projectile movement and impacts.
- Entity spawning, death, removal, and replacement.
- Vehicles, passengers, leashes, and related entity groups.
- Teleports between positions in the same owner, separate owners, and separate worlds.
- Respawn and player world transfer.
- Block placement, breaking, and interaction.
- Neighbor updates, including observers and comparators.
- Redstone wire propagation, torches, repeaters, rails, and long-distance update chains.
- Pistons and multi-block movement.
- Fluids and cascading updates.
- Explosions and area effects spanning multiple domains.
- Hoppers, inventories, block entities, and transfers between containers.
- Mob pathfinding and target selection across boundaries.
- Villagers and point-of-interest systems.
- Chunk unloads, reloads, and entity transfers around those operations.
- Entity tracking and packet replication.
- Player lists, chat, scoreboards, teams, and global game state.

For each feature, state whether the initial architecture supports it directly, coordinates it through messages, requires a transaction, needs a snapshot, or must initially execute under a larger exclusive ownership scope.

Do not silently alter vanilla mechanics as a convenient solution to a concurrency problem.

Where behavior cannot be preserved cheaply or safely, document the exact limitation and recommend a staged approach.

# 11. Tick semantics and scheduling guarantees

Choose an explicit model for simulation time.

Folia's regional tick loops are not simply a single main-thread loop divided into simultaneous substeps. Torch must define its own timing and coordination rules.

Compare:

- One global tick epoch for the world.
- Independently progressing ownership domains.
- A hybrid with locally scheduled simulation and explicit global coordination.

For each alternative, analyze synchronization cost, lag isolation, cross-boundary semantics, global time, scheduler behavior, and gameplay ordering.

Recommend one and explain why.

The architecture must define:

- What the nominal tick period means.
- Whether 20 TPS is a target, a hard guarantee, or both under different circumstances.
- How an overloaded owner behaves.
- Whether an owner is allowed to run behind independently.
- Whether simulation time can diverge across domains and how that affects mechanics.
- The distinction between simulation time, wall-clock time, and asynchronous completion time.
- How delayed tasks behave when an owner is stalled.
- The ordering of input, entity updates, block ticks, physics, scheduled tasks, and replication.
- Whether each order is globally defined, domain-local, or system-specific.
- How changing execution order is evaluated against vanilla compatibility.

Do not force expensive barriers between all domains unless measurements and semantics justify them.

Do not hide tick starvation by reporting only average TPS.

Define per-owner and system-level latency metrics so a single overloaded area cannot disappear inside healthy aggregate statistics.

# 12. Parallel compute subsystem

Design a clearly separated computation system.

Workers may perform expensive calculations concurrently, but they must not acquire unrestricted authority over live world state.

For each off-thread computation, specify its contract:

- Immutable input.
- Snapshot creation or acquisition.
- Snapshot lifetime and memory cost.
- Input versioning.
- Calculation deadline or cancellation policy.
- Result type.
- Validation requirements.
- Publication mechanism.
- Owner responsible for applying the result.
- Behavior if the result is stale.
- Backpressure and admission policy.

The result path must never require a blocked simulation owner to wait for an overloaded compute pool while that pool waits for the simulation owner.

Evaluate separate bounded pools or scheduling classes for:

- CPU-intensive world computation.
- Blocking storage and filesystem work.
- Network processing.
- Serialization and compression.
- Other tasks discovered in the audit.

Avoid both extremes: one global pool in which blocking I/O can starve simulation, and an uncontrolled collection of executors whose combined thread counts oversubscribe the machine.

Use the project's actual JVM and build constraints when selecting implementation techniques.

The design should be able to account for container CPU limits, hardware concurrency, background services, and garbage-collection threads without assuming every reported logical CPU is available for ticking.

18. Region-Based Execution

Torch should be capable of exploiting multiple CPU cores.

A Folia-like region execution model is a strong architectural direction.

However, do not blindly copy Folia internals.

The goal is the underlying property:

«Independent areas of the world should be able to simulate independently when their state does not conflict.»

A possible architecture:

                 Worker Pool
        +----------+----------+
        |          |          |
     Worker A   Worker B   Worker C
        |          |          |
      Region     Region     Region
        |          |          |
      World      World      World

Workers are resources, not permanent per-player threads.

Do NOT create:

500 players = 500 permanent threads

Instead:

many regions
      ↓
scheduled work
      ↓
shared worker pool
      ↓
workers execute active regions

Idle workers should not consume significant CPU merely because the server is configured with a worker count.

Each simulated region should have a clear owner/execution context.

A large separation distance can be used as a safety heuristic, but do not treat arbitrary distances such as 500 blocks as a fundamental correctness rule.

Minecraft interactions can cross region boundaries through:

- projectiles,
- explosions,
- knockback,
- redstone,
- pistons,
- fluids,
- block updates,
- entity targeting,
- mobs,
- teleportation,
- plugin operations,
- chunk operations.

Therefore, correctness cannot rely solely on geographic distance.

34. Performance Philosophy

Performance matters.

But:

Correct 1.8.8 behavior
>
better benchmark number

Never change vanilla behavior merely because a different implementation benchmarks faster.

Optimize after measuring.

Use profiling to identify actual bottlenecks.

Prefer:

- reduced allocations,
- cache-friendly structures,
- efficient scheduling,
- localized state,
- batch processing,
- region ownership,
- efficient networking,
- appropriate data structures.

Avoid:

- global locks,
- unnecessary synchronization,
- premature abstraction,
- unsafe concurrency,
- giant shared mutable structures.

46. Final Engineering Rules

Always follow these rules.

Rule 1

Build Torch, not a renamed Minestom.

Rule 2

The native API belongs to "net.zaminmc.torch.*".

Rule 3

Mirror familiar Bukkit/Spigot/Paper package structures for native equivalents whenever practical, changing the root namespace to "net.zaminmc.torch".

Rule 4

Bukkit, Spigot, and Paper namespaces remain compatibility namespaces.

org.bukkit.*
org.spigotmc.*
io.papermc.paper.*

Rule 5

There is one authoritative game state.

Rule 6

Native API and compatibility APIs operate on that same state.

Rule 7

Design the native API before allowing engine implementation details to accidentally become the public contract.

Rule 8

Minestom is internal infrastructure, not Torch's identity.

Rule 9

Minecraft 1.8.8 behavior must be reproduced rather than approximated.

Rule 10

Region execution must preserve gameplay correctness.

Rule 11

Workers are shared execution resources, not one permanent thread per player.

Rule 12

Cross-region interactions require explicit coordination.

Rule 13

Never use a global lock as the default solution to concurrency.

Rule 14

Never invent benchmark results.

Rule 15

Never mark unverified behavior as verified.

Rule 16

Never destroy existing user work.

Rule 17

Never hide incomplete implementation behind fake return values.

Rule 18

Prefer slow, correct engineering over fast, fragile progress.

Rule 19

Do not rewrite working code without evidence.

Rule 20

When uncertain about an irreversible architectural decision, stop and ask rather than guessing.

Final Directive

Build Torch as a long-term Minecraft server platform.

Establish its native API carefully.

Make that API familiar enough for Bukkit/Spigot/Paper developers to understand immediately, while giving Torch ownership over its own architecture and future.

Use Minestom where it provides useful infrastructure, but never allow the dependency to define Torch's identity.

Create one authoritative simulation state.

Make the native API and compatibility APIs operate against that state.

Build faithful Minecraft 1.8.8 mechanics.

Design the execution model around explicit ownership, regions, workers, and safe cross-region coordination.

Preserve legacy plugin behavior where compatibility requires it.

Measure everything important.

Test behavior rather than class existence.

Document what is actually implemented.

Do not optimize for appearing finished.

Do not optimize for benchmark screenshots.

Do not optimize for the smallest number of commits.

Optimize for building a server that can still be understood, maintained, extended, and trusted years from now.

Torch is allowed to take a long time.

Do it properly.
